# Development

## Layout

- `eu.nosini.Artemis.yml`: the Flatpak manifest.
- `eu.nosini.Artemis.metainfo.xml` and `.desktop`: software-center metadata
  and launcher. The icon comes from upstream.
- `nuget-sources.json`: the pinned NuGet packages, generated by
  `scripts/generate-dotnet-deps.sh`.
- `patches/`: changes to the upstream source, applied in order.
- `launcher/artemis`: the command the Flatpak runs.
- `flathub.json`: limits the build to x86_64.
- `lint-exceptions.json`: linter errors that don't apply to a self-hosted
  repository, each with its reason.
- `tests/check-installed.sh`: checks that run inside the installed app.
- `scripts/test-installed.sh`: installs a local build and runs those checks.
- `scripts/prepare-repository.sh`: signs tested builds for publishing.
- `scripts/check-sources.sh`: runs the update checker, and regenerates the
  NuGet sources for a new release.
- `scripts/update-upstream.sh`: turns the update checker's changes into a
  pull request.
- `scripts/tests/`: tests for these scripts.
- `scripts/builder-tools.sh`: fetches the pinned
  [flatpak-builder-tools](https://github.com/flatpak/flatpak-builder-tools).

An upstream checkout in `upstream/` is ignored by Git. It is handy for
reading the source and for making patches.

## How the package works

Artemis is a .NET application with an [Avalonia](https://avaloniaui.net/)
user interface. The `artemis` module builds the published release's commit
from source with the .NET SDK from the
`org.freedesktop.Sdk.Extension.dotnet10` extension, the way upstream's own
CI builds its Linux release: `dotnet publish` of
`src/Artemis.UI.Linux` as a self-contained app for `linux-x64`. The result,
with the .NET runtime, goes to `/app/lib/artemis`. Upstream's Linux project
only targets x64, so `flathub.json` limits the build to x86_64.

The build has no network access. `dotnet publish` restores the NuGet
packages from `nuget-sources/`, which flatpak-builder fills from
`nuget-sources.json`, and the .NET runtime packs from the SDK extension's own
package folder, so they always match the SDK that builds the app.
StrawberryShake's GraphQL code generator, which runs during the build,
targets .NET 9; `DOTNET_ROLL_FORWARD=Major` lets it run on .NET 10.

Artemis has no Git tags. Its CI numbers each build `1.YYYY.MMDD.N` by date,
and its update server publishes some of them as releases. The manifest pins
the commit of a published release. The build passes the version of the
newest release in the metainfo file to `dotnet publish`, so Artemis shows and
reports the same version as upstream's build of that commit. Without a
version, Artemis would call itself `local`.

`launcher/artemis`, installed as `/app/bin/artemis`, starts
`Artemis.UI.Linux` with `--disable-updating`. That argument comes from
`patches/0001-disable-updating-argument.patch`: Artemis would otherwise
download new releases into its data folder and try to replace its own files,
which are read-only in a Flatpak. With the argument, it neither looks for
releases nor offers or installs them, and **Check now** explains why.
Workshop entries keep updating.

The upstream icons are installed under the app ID. The desktop file and the
metainfo are written here, since upstream has neither.

### Permissions

- `--share=network`: Artemis reaches device servers such as OpenRGB's SDK
  server on `127.0.0.1:6742`. Sharing the network namespace means the
  sandbox's localhost is the host's, so nothing else is needed for that.
  The same permission covers the Workshop and Artemis's local web server.
- `--socket=x11` with `--share=ipc`: Avalonia 11 has no Wayland backend.
- `--device=dri`: OpenGL rendering of the window.
- `--talk-name=org.kde.StatusNotifierWatcher` and
  `--own-name=org.kde.StatusNotifierItem-2-0`: Avalonia's tray icon owns a
  well-known name built from the process ID and the icon's number instead of
  registering its unique name. Artemis is process 2 in the sandbox and has
  one tray icon. If the proxy refused the name, the registration would fail
  and no tray icon would appear. The linter's error for the name is an
  exception in `lint-exceptions.json`.

No device access is granted. Artemis drives hardware through OpenRGB, whose
service has its own permissions. Its direct device providers, which use HID
and USB, and its keyboard input provider, which reads `/dev/input`, don't
work in the sandbox.

## Building

The simplest way to build is with `org.flatpak.Builder` from Flathub. It
contains flatpak-builder and the linter in the versions Flathub uses:

```sh
flatpak install --user flathub org.flatpak.Builder
flatpak run org.flatpak.Builder --user --install --install-deps-from=flathub \
  --default-branch=stable --force-clean --repo=repo build-dir eu.nosini.Artemis.yml
```

The build downloads the pinned sources, so it needs a network connection.
Building from a checkout installs the app from a local remote named
`eu.nosini.Artemis-origin`. Once the build directories are gone,
`flatpak update` warns that it can't reach it. Switch to the published
remote as the README describes, or disable it with
`flatpak remote-modify --user --disable eu.nosini.Artemis-origin`.

To get a single-file bundle instead of installing:

```sh
flatpak build-bundle --runtime-repo=https://dl.flathub.org/repo/flathub.flatpakrepo \
  repo artemis.flatpak eu.nosini.Artemis stable
```

## Checking

CI uses Flathub's manifest and exported-repository linter. It validates the
metainfo without network access, so an unreachable upstream website or
screenshot server cannot fail that check. Run the checks locally with:

```sh
alias lint='flatpak run --command=flatpak-builder-lint org.flatpak.Builder'
lint --exceptions --user-exceptions lint-exceptions.json manifest eu.nosini.Artemis.yml
flatpak run --command=appstreamcli org.flatpak.Builder validate --no-net --explain \
  eu.nosini.Artemis.metainfo.xml
lint --exceptions --user-exceptions lint-exceptions.json repo repo
```

To check live links and screenshot availability separately, run
`lint appstream eu.nosini.Artemis.metainfo.xml`. This needs the upstream
websites to be reachable.

Only add an exception when the rule doesn't apply to a package published
outside Flathub, and say why in `lint-exceptions.json`.

To run the checks inside the installed app, build without `--install` (but
with `--repo=repo`), then run:

```sh
bash scripts/test-installed.sh
```

The script adds a `local-test` remote for `repo/`, installs the app from
it and runs `tests/check-installed.sh` with `flatpak run`, so the checks see
the Platform runtime the app runs with, not the SDK. It refuses to replace
an existing installation. Afterwards, remove the test installation with
`flatpak --user uninstall eu.nosini.Artemis` and the remote with
`flatpak --user remote-delete local-test`.

## Debugging

A shell in the sandbox of the last build, without installing it:

```sh
flatpak run org.flatpak.Builder --run build-dir eu.nosini.Artemis.yml sh
```

A shell in the installed app's sandbox, with the SDK and its debugging tools
in place of the Platform runtime (the SDK must be installed):

```sh
flatpak run --devel --command=sh eu.nosini.Artemis
```

To see which D-Bus names the app tries to reach, and so which `--talk-name`
permissions it needs:

```sh
flatpak run --log-session-bus eu.nosini.Artemis 2>&1 | grep '(required 1)'
```

Permissions granted through portals, such as notifications or background
running, are listed with `flatpak permission-show eu.nosini.Artemis` and
cleared with `flatpak permission-reset eu.nosini.Artemis`.

## GitHub Actions

`.github/workflows/flatpak.yml` runs when a `v*` version tag is pushed,
for pull requests and on manual runs. Pushes to `main` run the packaging
checks without building the app. Release builds use the tagged commit of
this packaging repository. For each architecture, it lints the manifest and
metainfo, builds with
[flatpak-github-actions](https://github.com/flatpak/flatpak-github-actions),
lints the exported build, runs the installed-app checks and uploads an
installable bundle as an artifact. Install a downloaded artifact with
`flatpak install --user artemis-x86_64.flatpak`. Bundles are unsigned and
don't update; the published repository does.

Like Flathub, CI builds the architectures that `flathub.json` allows, here
x86_64 only.

`.github/workflows/checks.yml` lints the scripts and workflows, checks that
the manifest and metadata files parse, and runs the tests in
`scripts/tests/`. The publishing test makes small fake builds and publishes
them several times to a local web server.

### Publishing

When the repository variable `PUBLISH_FLATPAK` is `true`, pushing a
stable version tag builds and publishes a signed Flatpak repository to
GitHub Pages. A manual Flatpak run on `main` also publishes, so packaging
fixes can be shipped without a new upstream release. Pull request builds,
prerelease builds and manual builds on other branches produce bundle
artifacts without publishing. After a tag build passes, the workflow
creates its GitHub Release using the runner's `GITHUB_TOKEN` and attaches
the tested `artemis-x86_64.flatpak` bundle. Stable publication must complete
the Pages deployment before release creation. If publication is disabled,
tag builds still create GitHub Releases with their bundles. Manual runs on
version tags follow the same release flow. Reruns replace assets on an
existing release and finish publishing a draft left by an interrupted run.
Prerelease tags produce GitHub prereleases and cannot become the latest
stable release.

A separate job, which never runs upstream build code, downloads the
published repository and checks it against the signing key.
It adds the tested builds of all architectures as new signed commits,
generates static deltas, signs a new software catalog and summary, and
writes `artemis.flatpakrepo` and `artemis.flatpakref` with the public key
embedded. Both files take the app's
summary from its metainfo and point to a copy of its icon, which software
centers show when the remote or app is added. Before deploying, a fresh
remote that only knows the public key must accept the result.

The repository keeps the five previous versions of the app and each
extension, so users can go back to one with `flatpak update --commit`. A
build whose files didn't change adds no version. Static deltas let Flatpak
download an install or update as a few large files instead of one request
per file. They add about a third to the repository's size, and each kept
version adds only the files that changed. If the published repository can't
be downloaded or doesn't match the signing key, for example after replacing
the key, the job fails. Set the variable `FLATPAK_KEEP_HISTORY` to `false`
to publish a new repository without the earlier versions.

The repository URL defaults to `https://OWNER.github.io/REPOSITORY/`. For a
custom domain, set the `FLATPAK_REPO_URL` variable to the real URL,
including the trailing slash.

To set publishing up:

1. In **Settings → Pages**, select **GitHub Actions** as the source. If the
   `github-pages` environment restricts deployment branches and tags, allow
   a Tag rule for `v*` and retain a Branch rule for `main` for manual
   publishing. Branch and tag rules are separate.
2. Store the signing key as the secret `FLATPAK_GPG_PRIVATE_KEY` (see
   below).
3. Set the variable:
   `gh variable set PUBLISH_FLATPAK --body true --repo nosini/artemis-flatpak`.
4. Push a version tag pointing to the packaging commit to build, or run the
   Flatpak workflow manually on `main`.

Stable tags follow Artemis's four-part version, for example
`v1.2026.0101.2`. A numeric suffix such as `v1.2026.0101.2-1` is a stable
packaging revision of the same upstream version. Other suffixes, such as
`v1.2026.0101.2-rc1`, produce prereleases without replacing the stable
Flatpak repository. Tag the packaging commit containing the intended pins
and workflow; creating the GitHub Release manually is unnecessary:

```sh
git tag -s v1.2026.0101.2 -m 'Artemis 1.2026.0101.2'
git push origin v1.2026.0101.2
```

### Signing key

The key has to be an ASCII-armored GnuPG private key without a passphrase.
An existing Flatpak signing key can be reused. To make a new one, generate
it on your own machine, outside the source checkout, in a separate GnuPG
directory:

```sh
mkdir -p -m 700 "$HOME/.gnupg-flatpak/private-keys-v1.d"
gpgconf --homedir "$HOME/.gnupg-flatpak" --create-socketdir
gpg --homedir "$HOME/.gnupg-flatpak" --batch --pinentry-mode loopback \
  --passphrase '' --quick-generate-key 'Nosini Flatpak signing' ed25519 sign 0
```

Upload it through a private temporary file, so a failed export can't upload
an empty secret:

```sh
(
  set -eu
  umask 077
  key_file=$(mktemp "$HOME/.gnupg-flatpak/export.XXXXXX")
  trap 'rm -f "$key_file"' EXIT
  gpg --homedir "$HOME/.gnupg-flatpak" --armor \
    --export-secret-keys 'Nosini Flatpak signing' > "$key_file"
  test -s "$key_file"
  gh secret set FLATPAK_GPG_PRIVATE_KEY --repo nosini/artemis-flatpak < "$key_file"
)
```

Keep a backup of the key. Installed copies trust the public key from the
`.flatpakref` they were installed with, so replacing the key breaks their
updates.

### Shared remote

[flatpak-repo](https://github.com/nosini/flatpak-repo) collects the
published packages into the shared `nosini` remote. After the first
publication, add an entry for this app to its `apps.json`, listing every
extension the build exports (`Locale` when the app has translations).

## Updating

`.github/workflows/update.yml` runs
[flatpak-external-data-checker](https://github.com/flathub-infra/flatpak-external-data-checker)
every Monday at 05:17 UTC, and on manual runs. Since Artemis has no tags, its
`x-checker-data` asks Artemis's update server
(`updating.artemis-rgb.com/graphql/`) for the newest published Linux release
of the `master` channel, with its version, commit and date. This is the
release Artemis's own updater would install. When it is a different commit,
the checker updates the pin and adds the release to the metainfo file.
`scripts/check-sources.sh` then regenerates `nuget-sources.json` for the new
commit (see [.NET dependencies](#net-dependencies)). It does this in Flathub's
CI image, which can run the SDK in a privileged container. The workflow
pushes the changes to the `update/upstream` branch, opens a pull request and
starts the Flatpak build of that branch. Its result shows on the pull
request. After merging, push a version tag at the merged commit to
build and publish the update.

The workflow needs **Allow GitHub Actions to create and approve pull
requests** under **Settings → Actions → General**.

To merge updates without review, set the variable `AUTO_MERGE_UPDATES` to
`true`. The workflow then waits for the build and merges the pull request
when the build and the installed-app checks pass. Push a version tag
afterwards to ship it. A failed build leaves the pull request open.

Changes pushed to `update/upstream` by anyone but the workflow are kept:
while the pull request is open, later runs commit newer releases on top of
them, comment on the pull request and leave it for review even with
`AUTO_MERGE_UPDATES`. Once the pull request is closed or merged, the next
update starts again from `main`. If someone pushes to the branch while the
workflow runs, the run fails instead of replacing the branch; the next one
picks the push up.

GitHub disables scheduled workflows in public repositories after 60 days
without activity. Artemis publishes releases rarely, so this is likely.
Re-enable the workflow under **Actions** when it happens.

A patch that no longer applies fails the build. Check out the new commit in
`upstream/`, make the change again, regenerate the patch with
`git format-patch` and then the NuGet sources, and push both to the update
branch. A new release that needs a newer .NET also fails; see
[Moving to a newer runtime or .NET](#moving-to-a-newer-runtime-or-net).

## .NET dependencies

`nuget-sources.json` lists every NuGet package the build restores, with its
download URL and SHA-512. After changing the pinned commit or a patch,
regenerate it:

```sh
flatpak install --user flathub org.freedesktop.Sdk//26.08 \
  org.freedesktop.Sdk.Extension.dotnet10//26.08
bash scripts/generate-dotnet-deps.sh
```

The script fetches the pinned commit into `.cache/artemis-source`, applies
the patches, and runs `flatpak-dotnet-generator` from the pinned
flatpak-builder-tools. That runs `dotnet restore` for `linux-x64` as a
self-contained app inside the SDK with its .NET extension, and lists what
was downloaded. The generator ignores restore errors, so the script checks
that the result has the packages every Artemis build needs. It also leaves
out the .NET runtime packs, which the build takes from the SDK extension.

The list includes some packages in several versions, Avalonia for example.
NuGet downloads every version it considers while resolving dependencies, and
the offline restore needs the same ones.

`scripts/tests/test-generate-dotnet-deps.sh` tests the script with a fake
`flatpak` command and a local repository.

## Moving to a newer runtime or .NET

For a new runtime, change `runtime-version` in the manifest and the image
tag in `.github/workflows/flatpak.yml` (`freedesktop-26.08`), make sure the
`org.freedesktop.Sdk.Extension.dotnet10` extension exists for it, and
regenerate the NuGet sources.

When Artemis moves to a newer .NET, replace `dotnet10` everywhere: the
manifest's `sdk-extensions` and `build-options`, the publish command's
`--source`, and `dotnet` in `scripts/generate-dotnet-deps.sh` and
`scripts/check-sources.sh`. Then regenerate the NuGet sources.
